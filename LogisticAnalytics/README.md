# LogisticAnalytics - Портал отчётов складской логистики

Клиентский портал складской аналитики: PWA на чистом HTML/CSS/JavaScript. Работает в браузере, данные обрабатываются локально и сохраняются в IndexedDB. Сервер, сборка и установка зависимостей для работы портала не требуются.

## Как запустить

1. Скопируйте папку проекта на компьютер или разверните на статическом сервере.
2. Откройте `index.html`:
   - для полноценной PWA (установка, офлайн, обновления) нужен `localhost` или HTTPS;
   - при открытии через `file://` часть браузеров ограничивает IndexedDB и Service Worker.
3. В каждом сервисе загрузите `.xlsx` через зону загрузки. Данные сохраняются в IndexedDB и восстанавливаются после перезагрузки.

Сборка не нужна: все страницы - обычные HTML-файлы со встроенными `<style>` и `<script>`.

## Версии и обновления

Единый источник версий - `shared/js/config.js`:

```js
self.PORTAL_CONFIG = Object.freeze({
    version: '1.0.7',
    releaseDate: '27.11.2026',
    services: [
        // { id, title, version, icon, url, desc, accent, grad, glow }
    ],
});
```

Как это работает:

- главная страница строит карточки сервисов из `PORTAL_CONFIG.services`;
- каждый сервис подключает `shared/js/config.js` и помечает шапку/подвал атрибутом `data-version-service="<id>"`; версия подставляется автоматически;
- в интерфейсе версия сокращается до двух компонентов: `1.0.0` → `v1.0`;
- `package.json` содержит ту же версию портала; совпадение проверяет `test/config.test.js`;
- Service Worker импортирует `shared/js/config.js` и строит имена кэшей из версии портала:
  - `lemanapro-portal-1-0-7` - оболочка;
  - `lemanapro-portal-runtime-1-0-7` - динамические ресурсы `shared/`.
  Точки заменяются на дефисы. При новой версии создаётся новый кэш, старые удаляются при активации.

### Как применяется обновление

- Service Worker не активируется молча: в `install` нет `skipWaiting`.
- Страница периодически (раз в 15 минут и при возврате на вкладку) проверяет `shared/js/config.js`; Service Worker проверяет версию не чаще раза в 60 секунд.
- При расхождении версий портал показывает уведомление «Доступна новая версия» с кнопками «Обновить» / «Позже».
- Перезагрузка происходит только после подтверждения пользователя.
- Если изменился только `config.js` и нового Worker нет, активный Worker получает `APPLY_UPDATE`, обновляет кэши, после чего страница перезагружается.

### Порядок выпуска

1. Обновить `version` портала и при необходимости версии сервисов в `shared/js/config.js`.
2. Обновить `version` в `package.json`.
3. Добавить запись в `NEWS_CHANGES` в `index.html` (дата и текст изменений).
4. Если добавлен новый сервис - зарегистрировать его в `PORTAL_CONFIG.services` и добавить `./Services/<папка>/index.html` в `SHELL` в `sw.js`.
5. Прогнать тесты из корня проекта: `node --test`.
6. Проверить, что версия в `package.json` совпадает с `PORTAL_CONFIG.version`, а в HTML сервисов нет захардкоженных версий.

## Тесты

Тесты запускаются в Node.js (18+) без установки npm-зависимостей. Рабочая директория должна быть корнем проекта: тесты используют относительные пути `./Services/...`, `./shared/...` и `./not indexed/samples_XLSX/...`.

- при изменении порядка `<script>` в сервисе тесты могут сломаться;

- существование страниц сервисов на диске;

- что сервисы подключают `config.js` и `pwa-update.js`;
- что в разметке нет захардкоженных версий.

## Сервис «Аномалии склада» (слияние двух отчётов)

Сервис объединяет две выгрузки и отвечает на вопрос «где искать аномальный артикул».

| Отчёт | Что берём | Ключ |
|---|---|---|
| 1. «Список аномалий запаса» (Power BI) | артикул, отдел, гамма, наименование и отклонения по магазину | `Артикул` |
| 2. «Содержимое ячеек» (WMS Navision) | фактическое наличие на адресах: зона, ячейка, тип ячейки, наличие, свободно, в подборе, паллета, сумма | `LM Код` |

- **Отклонения**: «В торговом зале», C3, экспо и отрицательная доступность показываются отдельно и не суммируются между собой. Термин «дефицит» в интерфейсе не используется как избыточный.
- **Слияние** выполняется по коду артикула (`Артикул` ↔ `LM Код`); анализ запускается только после загрузки обоих отчётов.
- **Один экран**: три показателя → зона «Аномальные артикулы - где искать на складе» с тремя графиками в ряд (артикулы по отделам, круговая диаграмма по зонам склада и топ-10 ячеек) → рабочий список аномалий с карточкой артикула.
- На графиках считается **SKU** - количество уникальных аномальных артикулов, а не штук на складе. Термин единый - SKU.
- **Фильтры списка**: по умолчанию показаны только найденные на складе позиции. После нажатия «Показать всё» в шапке списка появляются кнопки «Только найденные» и «Нет на складе» - они стоят в одной строке с «Показать всё» и переключают список между найденными, отсутствующими и всеми аномалиями.
- **Ненайденные позиции**: остатки из отчёта аномалий по зонам RM, ЕМ, RD и буферу склада остаются в карточке артикула, но перечёркиваются - фактически на складе этих количеств уже нет.
- **Список аномалий**: у каждого артикула вместо гаммы показывается количество на складе в штуках по отчёту фактического наличия (у ненайденных - 0 шт.), отдел и зоны находок - все шильдики стоят в одну строку, без денежной суммы.
- **Две панели**: список слева и детализация справа имеют одинаковую высоту; длинная детализация прокручивается внутри правой панели, пустое состояние выровнено по центру.
- **Оформление**: палитра «Золото / Графит» как в «AVS Контроль» - золотой градиент фона, тёмная шапка с жёлтой линией, кремовые зоны загрузки и сообщений, цветные карточки показателей и тёмные заголовки панелей. Информационное окно собрано по образцу AVS: пронумерованные шаги, карточки-пояснения и блок «Важно знать».
- **Действия с найденными позициями**: копирование адресов в буфер и печатное задание для сборщика.
- **Особенность разбора**: книга читается без преобразования дат (`cellDates: false`) - в выгрузке встречаются ячейки-суммы с «дата-форматом», которые иначе превращаются в объект `Date`. Числа читаются в форматах `−47`, `103.5`, `1,5`, `431,873.44`.
- **Пример файла**: `not indexed/samples_XLSX/anomalies_Список аномалий запаса.xlsx` и `not indexed/samples_XLSX/anomalies_содержимое ячеек.xlsx`. Кнопки «Загрузить пример» в интерфейсе нет.

## Сервис «Оперативные инвентаризации по адресу»

Сервис анализирует отчёт `WMS Navision → Подразделения → Склад → Отчёт по проведённым оперативным инвентаризациям` и отвечает на вопросы: сколько инвентаризаций по адресу провели, какие ведомости завершены, где недостачи и излишки и сколько времени занимают подсчёты.

### Логика данных

- **Ведомость** - уникальный `№ Ведомости`. В одной ведомости может быть несколько ячеек, паллет и товарных строк; строки не схлопываются.
- **Дата периода** - `Дата Учёта`; для ведомостей «В процессе» используется `Дата назначения`, чтобы они не выпадали из периода.
- **Дельта** - `Результат подсчёта − На начало подсчёта`. Отрицательная дельта - недостача, положительная - излишек.
- **Оборот расхождений** - сумма абсолютных дельт. Показывает масштаб расхождений, даже если недостача и излишек взаимно компенсируются.
- **ТОП-10** строится отдельно по недостачам и по излишкам; переключатель «Недостачи / Излишки» есть у обеих карточек.
- **Длительность** - `Время Учёта − Время назначения`; считается только для завершённых ведомостей со статусом `Учтено`.
- **Тип задания** и **тип инвентаризации** - фильтры скрываются, если в данных только одно значение.
- **Опечатка исходного отчёта** `Тип инвентризации` поддерживается как есть; в интерфейсе используется правильное название «Тип инвентаризации».
- **Строки без паллеты** показываются с «-» и не увеличивают количество уникальных паллет.
- **Строка и артикул - разные вещи.** Строка - одна запись отчёта: товар в конкретной ячейке и паллете. Один артикул может встречаться в нескольких строках, ячейках и ведомостях. «Строк подсчёта» - все записи отчёта, «Артикулов» - уникальные коды товара.

### Интерфейс

- 4 KPI-карточки: ведомости, строки подсчёта, ячейки, ведомости с расхождениями; в подписях видны паллеты и количество уникальных артикулов.
- В ленте сводки отдельно выводятся «Строк подсчёта» и «Артикулов».
- 4 графика: динамика по дням (стековые столбцы - ведомости, шт.; линия - строки подсчёта, шт.), структура расхождений, сотрудники, длительность.
- Все количественные показатели подписаны в штуках: «На начало, шт.», «Результат, шт.», «Дельта, шт.», «Недостача, шт.», «Излишек, шт.», «Оборот, шт.».
- Период выбирается ползунком диапазона дат с гистограммой по дням и пресетами «Весь период», «7 дней», «Последний день».
- Два ТОП-10 с переключением «Недостачи / Излишки»: ведомости и артикулы.
- Реестр ведомостей с сортировкой, пагинацией, поиском и карточкой ведомости: дата, время, длительность, сотрудник, ячейки, паллеты, артикулы, строки, расхождения, дельта и статус. В карточке - агрегаты, чипы ячеек, таблица строк и фильтр «Только расхождения».
- Карточка артикула открывается из ТОП-10 артикулов: все строки артикула по ведомостям, переход к ведомости по клику.
- Фильтры применяются ко всему дашборду: KPI, графики, ТОП-10 и таблица.
- Варианты фильтра «Расхождения» взаимоисключающие: «Без расхождений», «Только недостача», «Только излишек», «Смешанные». Статус «В процессе» нельзя сочетать с расхождениями - у такой ведомости они ещё не рассчитаны.
- Фильтры каскадные: список сотрудников, заданий и типов инвентаризации сужается под выбранный период и остальные фильтры, а недоступные статусы и категории расхождений в списках не показываются.
- Экспорт XLSX: листы «Сводка», «Ведомости», «Строки», «Сотрудники»; учитываются активные фильтры, в сводке есть строка «Товаров (артикулов)».
- Данные сохраняются в IndexedDB: `lemanapro_operativ_inventory`, хранилище `kv`, ключ `operativ_inventory_report`.
- Пример файла: `not indexed/samples_XLSX/OperativInventory.xlsx`; кнопки загрузки примера в интерфейсе нет - файл используется тестами и ручной проверкой.

### Текущий пример

- 2 345 строк, 237 ведомостей, 369 уникальных ячеек, 962 паллеты, 1 575 артикулов, 14 сотрудников.
- 0 ведомостей «В процессе»; 47 ведомостей с расхождениями и 136 строк расхождений.
- Недостача −1 026,5 шт., излишек 1 306 шт., оборот 2 332,5 шт.
- Медиана длительности 19,28 мин, среднее 41,83 мин.
- Период 01.11-19.11.2026, 19 календарных дней; 11.11 - нулевой день без инвентаризаций.
- Самая большая ведомость - 209 строк, 15 ячеек, 207 паллет.
- Одна кросс-дневная ведомость: назначена 01.11, закрыта 02.11, длительность 23 ч 19 мин.

## Сервис «Оперативные инвентаризации по товару»

Отдельный тип инвентаризации: задания назначаются **по товару**, а не по адресу. Источник - `WMS Navision → Подразделения → Склад → Отчёт по проведённым оперативным инвентаризациям по товару`. Внешний вид и поведение повторяют сервис «Оперативные инвентаризации по адресу», но контекст - товары, зоны и денежные суммы.

### Логика данных

- **Ведомость** - уникальный `№ ведомости`. В одной ведомости может быть несколько товаров, заданий, ячеек и паллет; строки не схлопываются.
- **Дата периода** - дата и время завершения подсчёта; для незавершённых строк используется дата назначения.
- **Дельта количества** - `Фактическое Кол-во − Расчетное Кол-во`. Отрицательная - недостача, положительная - излишек.
- **Дельта суммы** - `Факт Сумма − Расчётная Сумма` в рублях; показывает денежный масштаб расхождения.
- **Длительность** - время завершения последней строки минус время назначения первой строки ведомости.
- **2-й подсчёт** - строки с непустым количеством второго подсчёта; **коррекция** - непустой `Номер документа коррекции`; **ошибка** - заполненный `Код завершения` (например, `SSCC НЕТ В АДРЕСЕ`).
- **Строки без паллеты** показываются с «-» и не увеличивают количество уникальных паллет.

### Интерфейс

- 4 KPI-карточки: ведомости, товары (уникальные артикулы), ячейки, ведомости с расхождениями.
- 4 графика: динамика по дням (стековые столбцы - ведомости, шт.; линия - строки подсчёта), структура расхождений, сотрудники (стековые строки подсчёта), дельта суммы по зонам (расходящиеся столбцы, ₽).
- Лента сводки: период, расчётное и фактическое количество, дельта, расчётная и фактическая сумма, дельта суммы, медиана и среднее длительности.
- Период выбирается ползунком диапазона дат с гистограммой по дням и пресетами.
- Два ТОП-10 с переключением «Недостачи / Излишки»: товары и ведомости.
- Реестр ведомостей: дата, время, длительность, сотрудники, товары, ячейки, паллеты, строки, расхождения, дельта количества и дельта суммы; сортировка, пагинация, поиск.
- Карточка ведомости: плитки количества и сумм, коррекции, вторые подсчёты и строки с ошибками, чипы ячеек, таблица строк и фильтр «Только расхождения».
- Карточка товара открывается из ТОП-10 товаров; клик по строке открывает ведомость с подсветкой строки.
- Фильтры (поиск, сотрудник, зона, расхождения, коррекции) применяются ко всему дашборду.
- Варианты фильтра «Расхождения» взаимоисключающие: «Без расхождений», «Только недостача», «Только излишек», «Смешанные».
- Фильтры каскадные: период сужает список сотрудников, сотрудник - список зон (только те, которые он считал), зона - список сотрудников; недоступные категории расхождений и коррекций в списках не показываются.
- Строка отчёта - это товар в конкретной ячейке и паллете; один товар может встречаться в нескольких строках. Поэтому «Товаров» и «Строк» считаются по-разному (подсказки в интерфейсе и раздел «Что считается»).
- Экспорт XLSX: листы «Сводка», «Ведомости», «Строки», «Товары», «Сотрудники»; учитываются активные фильтры.
- Данные сохраняются в IndexedDB: `lemanapro_operativ_inventory_goods`, хранилище `kv`, ключ `operativ_inventory_goods_report`.
- Пример файла: `not indexed/samples_XLSX/operativInventoryForGoods.xlsx`; используется тестами и ручной проверкой.

### Текущий пример

- 1 113 строк, 27 ведомостей, 276 товаров, 252 уникальные ячейки, 752 паллеты, 901 задание, 5 зон (U, Y, EM, RM, P), 14 сотрудников.
- Все 27 ведомостей завершены; 16 ведомостей и 64 строки с расхождениями (42 строки недостач, 22 строки излишков).
- Количество: расчётное 107 803 шт., фактическое 107 549 шт., дельта −254 шт.
- Суммы: 25 682 023,94 ₽ → 25 563 997,53 ₽, дельта −118 026,41 ₽; оборот расхождений 1 630 шт. и 414 616,87 ₽.
- 59 коррекций, 63 вторых подсчёта, 5 строк с заполненным кодом завершения.
- Период 01.11-19.11.2026, 19 календарных дней; 06.11 и 15.11 - нулевые дни без инвентаризаций.
- Самая большая ведомость - 659 строк, 62 ячейки, 640 паллет.
- Самая длинная ведомость - 226 минут.

## Сервис «Аналитика логистических операций»

Сервис отвечает на вопросы: как меняется объём операций по дням и часам, кто работает продуктивнее с учётом трудоёмкости, как выглядят подразделения и достоверность, и что именно делал конкретный сотрудник. Источник - та же выгрузка Power BI «Производительность сотрудников по операциям с товаром» (вкладка «Data»), что и у «Аналитики Операций Логистики», но с другим набором разрезов и метрик.

### Логика данных

- **Строка отчёта** - сотрудник выполнил операцию в конкретном контексте в 10-минутном слоте. Шаг времени фиксирован: 10 минут.
- **Контексты**: `SKU` (штуки), `PALLET` (паллеты), `ORDER` (заказы). Контекст нормализуется из колонки «Контекст операции».
- **22 операции** распределены по категориям:
  - **Приёмка** - «1я приемка», «Размещение с приемки»;
  - **Пополнение** - «Добавление товара на К», «Изменение вместимости», «Перенос товара между адресами», «Размещение на Z», «Разобрать с SSCC», «Списание с Z», «Удаление товара с адреса», «Комплектация из ТЗ»;
  - **Сборка и выдача заказов** - «Выдача заказа», «Перемещение сборки», «Размещение заказа», «Скатка маршрута», «Сборка в заказы»;
  - **Складские операции** - «Объединение», «Переукладка», «Подбор», «Размещение», «Перемещение в ТЗ», «Комплектация»;
  - **Достоверность** - «Достоверность» (инвентаризации торгового зала, преимущественно тип подразделения «коммерция»). Вынесена отдельной категорией.
- **Взвешенные операции** - `Кол-во операций × вес контекста`. Вес одинаков для всех операций и зависит только от контекста: **SKU - 2, паллета - 1, заказ - 1**.
- **КПД** - сумма взвешенных операций, делённая на сумму активных 10-минутных слотов сотрудников. Для группы, дня или часа складываются взвешенные операции и слоты входящих сотрудников, а не уникальные слоты всего склада.
- **Паллеты** - `Σ Кол-во операций` по строкам с контекстом `pallet`: одна операция = один паллет. **Штуки SKU** - `Σ Кол-во штук` только по строкам с контекстом `sku`.
- **Активные часы** - число уникальных пар «ЛДАП + дата + 10-минутный слот» × 10 / 60. Это время, когда сотрудник реально выполнял операции; перерывы, простои и обучение не входят.
- **Паллет/час** - `Паллеты / активные часы паллетных строк`; **Штук SKU/час** - `Штуки SKU / активные часы SKU-строк`; **SKU/час** - `SKU-операции / активные часы SKU-строк` (артикулы, не штуки); **Сборки/час** - `Сборки / активные часы строк операции «Сборка в заказы»`; **Заказы/час** - `Заказы / активные часы строк контекста order`. Это интенсивность в активное время, а не продуктивность по табелю.
- **Сборки** - это только операция «Сборка в заказы», а не весь контекст `ORDER`; в выгрузке она идёт с контекстом `SKU`, поэтому её часы входят в SKU-часы и не суммируются с ними.
- **Часы контекстов пересекаются**: один слот может содержать pallet, sku и order. Их нельзя суммировать и использовать как общий знаменатель; общие активные часы считаются по уникальным слотам сотрудника.
- **Порог ставки** - минимум 3 активных слота нужного контекста; если данных меньше, показывается `—`, а не 0.
- **Занятость** - активные часы и средняя занятость в активный день (`активные часы / активные дни`).
- **Сотрудники без ЛДАП или ФИО** (`нет данных`) исключаются из топ-карточек и карточек сотрудников, но остаются в общей динамике и суммарных операциях.
- **Подразделения** анализируются на вкладке «Продуктивность» через фильтры «Тип подразделения» и «Подразделение»: показываются все операции сотрудников выбранного подразделения, а не только профильные (пополнение, ОЗК - два отдела выдачи/обслуживания заказов, складские операции, внешний персонал).
- **Достоверность**: сотрудники с операцией «Достоверность» учитываются в одноимённой карточке категории; их строка в таблице открывает карточку со всеми операциями за период.

### Интерфейс

- **Единый период** сверху: ползунок диапазона дат с гистограммой по дням и пресетами «Весь период», «30 дней», «14 дней», «7 дней», «Последний день». Период применяется ко всем вкладкам.
- **5 вкладок**: «Продуктивность», «Контекстная продуктивность», «Динамика по дням», «Динамика по часам», «День и ночь».
- На каждой вкладке - 6 сводных карточек.
- **Контекстная продуктивность** - отдельная вкладка для операционной продуктивности по паллетам, штукам SKU, сборкам и заказам: шесть карточек (паллет/ч, штук SKU/ч, SKU/ч, сотрудники, активные часы, средняя занятость), топ-10 сотрудников и собственная таблица. Над топ-10 есть панель фильтров (контекст, тип подразделения, подразделение, должность, категория, операция и сброс) - та же, что над топ-10 вкладки «Продуктивность», но с **отдельным состоянием**: фильтры топ-10 не влияют на таблицу, а фильтры таблицы - на топ-10. Топ-10 сортируется по паллетам/ч, SKU/ч, штукам SKU/ч, паллетам, штукам, сборкам, сборкам/ч, заказам или заказам/ч, учитывает свои фильтры и порог активных слотов. Колонки таблицы: паллеты, паллет/ч, штуки SKU, штук SKU/ч, SKU/ч, сборки, сборки/ч, заказы, заказы/ч и активные часы. Таблица сортируется, фильтруется и экспортируется; если контекста у сотрудника нет или слотов меньше трёх, значения и ставки показываются как `—`, а не 0, и уходят в конец сортировки.
- **Продуктивность** - единая вкладка по всем людям: шесть карточек с числом сотрудников, **задействованных** в каждой категории операций (внешний персонал, пополнение, достоверность, приёмка, складские операции, сборка и выдача заказов); под числом подписано «задействовано», над карточками есть пояснение. Три круговые диаграммы (операции по категориям, структура по категориям во взвешенных операциях, контексты операций), топ-10 сотрудников и таблица. Внешний персонал считается по подразделению, остальные карточки - по категории операций; один сотрудник может попасть в несколько карточек. Подразделения выбираются фильтрами «Тип подразделения» и «Подразделение», поэтому отдельных вкладок для пополнения, ОЗК, склада и внешнего персонала нет. Топ-10 и таблицу можно сортировать по КПД, взвешенным операциям, слотам или количеству операций.
- **На каждой вкладке - 6 сводных карточек.** В таблице вкладки «Продуктивность» категория операций выбирается обычным фильтром, а не бейджами-вкладками; экспорт учитывает фильтры. Отдельным блоком ниже таблицы выводится **карта универсальности**: строки - сотрудники, столбцы - все категории операций, в ячейке - операции и их доля в работе сотрудника с мини-полосой, справа - всего операций, КПД и число категорий. Отдельных фильтров у карты нет: сверху расположены кнопки-уровни «Все» и «5 из 5» … «1 из 5» с числом сотрудников - они фильтруют карту по количеству закрытых категорий. В шапке показаны среднее число категорий и сколько человек закрывают все. Фильтры таблицы на карту не влияют.
- **«Динамика по дням», «Динамика по часам» и «День и ночь»** - без таблиц и топ-карточек.
- **Вкладка «Динамика по дням»** содержит блок «📈 Динамика по дням • разрез по контексту операций» из четырёх графиков в две строки: «Объём за период» по SKU / PALLET / ORDER, «Средний объём (штук SKU) по дням недели (пн-вс)», «Объём операций по категориям за период» и «Средний объём операций по дням недели (пн-вс)». В каждой строке линейный график шире, столбчатая диаграмма уже.
- **Вкладка «Динамика по часам»** собрана из двух блоков. Первый - «🕒 Операции по категориям за 24 часа»: пять столбчатых графиков (по одному на категорию) с подписями времени без поворота. Второй - «🔥 Тепловые карты»: «операции × часы» (22 операции) и «категории операций × часы» (5 категорий). Строки - операции или категории, столбцы - 24 часа, значение - количество операций. Тепловые карты подчиняются фильтрам блока графиков, выводятся целиком по высоте без вертикальной прокрутки и используют контрастный градиент от светло-мятного через изумрудный к медному. Отдельных графиков «Операции по часам», «Профиль 10-минутных слотов» и «Взвешенные операции по часам» на вкладке нет; суммы по строкам в тепловых картах не показываются.
- **Карточки «Динамики по часам»** показывают **три самых пиковых часа** каждой категории: приёмки, пополнения, ОЗК, складских операций и достоверности. Часы сортируются по количеству операций (при равенстве - по времени), в значении - часы через «·», в подписи - операции в эти часы. Если у категории нет операций по выбранным фильтрам, карточка показывает «-».
- **Вкладка «День и ночь»** сравнивает дневную смену (07:30-19:30) и ночную (19:30-07:30). Смена определяется по началу 10-минутного слота: день - слоты с 07:30 включительно до 19:30, остальные - ночь. На вкладке шесть карточек (операции, доли, соотношение день/ночь, КПД и число сотрудников по сменам), три **круговые диаграммы** («Операции: день и ночь», «Взвешенные операции: день и ночь», «Штуки: день и ночь (в общем)») и сводная таблица по категориям с долями внутри строки и КПД каждой смены. Карточки, диаграммы и таблица подчиняются фильтрам блока «Графики».
- **Фильтры разделены**: фильтры блока графиков действуют на графики и топ-карточки (на «Сотрудниках»), а на вкладках «Динамика по часам» и «День и ночь» - ещё и на сводные карточки и таблицу смен; фильтры таблицы (где таблица есть) действуют только на таблицу; у карты универсальности отдельный фильтр по числу категорий. Внутри каждой группы фильтры зависимые: каждый список (контекст, тип подразделения, подразделение, должность, категория, операция) строится по остальным активным фильтрам, поэтому недоступные значения не показываются, а выбранные ранее - сбрасываются. «Тип подразделения» не зависит от «Подразделения», чтобы тип можно было сменить при заданном подразделении; при смене типа чужое подразделение сбрасывается. При выборе категории в фильтре таблицы несовместимая операция сбрасывается, а категория остаётся. При переключении вкладок состояние фильтров не сохраняется - вкладка открывается с чистыми фильтрами. На вкладке «Контекстная продуктивность» такая же панель стоит прямо над топ-10, но с собственным состоянием: фильтры топ-10 не меняют таблицу, а фильтры таблицы не меняют топ-10.
- **Таблицы** (на вкладках, где они предусмотрены): сортировка по клику на заголовок, пагинация по 50 строк, поиск, экспорт в XLSX. На вкладке «Продуктивность» категория операций задаётся фильтром таблицы, а ниже отдельным блоком показывается карта универсальности сотрудников с фильтром по числу категорий.
- **Порог слотов** - выпадающий список в блоке «🏅 Топ-10» на вкладках «Продуктивность» и «Контекстная продуктивность»: «Все», от 5, 10, 20, 30, 50 или 100 активных слотов. Сотрудники ниже порога не показываются в топ-10; на графики и таблицу порог не влияет.
- **Топ-карточки** показывают взвешенные операции, КПД, количество операций и число слотов; в подписи - активные дни. Процентного рейтинга нет ни в карточках, ни в графиках, ни в таблице, ни в экспорте, ни в профиле.
- **Карточка сотрудника** открывается кликом по ФИО или топ-карточке: ссылка на `https://intraru.lemanapro.ru/profile/<ЛДАП>`, средние значения, динамика по дням в виде стека категорий операций, профиль по часам с тепловой картой, категории, контексты и топ операций. При открытии окна прокрутка страницы блокируется через `overflow: hidden` без `position: fixed`, поэтому позиция прокрутки сохраняется; ширина исчезнувшего скроллбара компенсируется отступом `body`.
- **Единая палитра** «Изумруд + медь»: тёмно-изумрудная шапка, медный акцент, мягкие зелёные поверхности. Переключателя палитр нет; справка открывается кнопкой «ℹ️» в шапке.

### AVS Контроль

Показывает SKU, количество, отделы, тепловую карту по зонам/датам, топ-10 критичных товаров и фильтры по отделу, зоне и срочности. Есть экспорт XLSX.

### Анализ Коррекций

Анализ отчёта по списанию товара. Три вкладки: «Коррекции» (списания и положительные коррекции без INV), «Инвентаризации» (строки INV: недостачи, излишки, дельта) и «Аномалии» (проверки по всему файлу). Учитывает самопроведение, сумму по цене DPAC, отсутствие утверждения/регистрации, нулевые количество и цену, долгую регистрацию и крупные количества. Есть режим «Ведомости» со сворачиванием строк, карточки сотрудников и документов, фильтры и экспорт XLSX.

Сервис принимает как книги, пересохранённые после открытия, так и файлы, сохранённые сразу после экспорта. Если Excel записал занижённый диапазон листа (`!ref`), общий модуль `parseXLSXFile` расширяет его по фактически заполненным ячейкам, поэтому строки не обрезаются.

## Деплой на GitHub Pages

Сайт публикуется workflow `.github/workflows/pages.yml`:
1. на каждый push в `main` и по ручному запуску собирается артефакт только из файлов сайта: `index.html`, `manifest.webmanifest`, `sw.js`, `robots.txt`, иконки, `shared/` и `Services/`;
2. артефакт публикуется через `actions/deploy-pages`.

Тесты в CI не запускаются: примеры XLSX исключены из git. Полный прогон `node --test` выполняется локально. Тесты, `not indexed/`, XLSX, `LogisticAnalytics/` и служебные конфиги, включая `opencode.json`, на сайт не попадают. Все пути в портале относительные, поэтому сайт работает и в подпапке `https://<user>.github.io/<repo>/`.

В настройках репозитория: **Settings → Pages → Build and deployment → Source: GitHub Actions**. После первого push workflow создаст окружение `github-pages` и выдаст URL.

Для локальной проверки сайта без тестов и примеров:

```bash
python -m http.server 8080
```

## Как добавить новый сервис

1. Создайте папку `Services/<имя>/` с `index.html`. Для новых папок лучше использовать латиницу без пробелов.
2. Добавьте запись в массив `services` файла `shared/js/config.js` (`id`, `title`, `version`, `icon`, `url`, `desc`, цвета). Главная страница подхватит её автоматически.
3. Подключите общие модули в правильном порядке:
   ```html
   <link rel="stylesheet" href="../../shared/css/common.css">
   <script src="../../shared/js/config.js"></script>
   <script src="../../shared/js/pwa-update.js"></script>
   <script src="../../shared/js-lib/xlsx.full.min.js"></script>
   <script src="../../shared/js-lib/chart.umd.min.js"></script>
   <script src="../../shared/js/idb.js"></script>
   <script src="../../shared/js/common.js"></script>
   ```
4. Укажите в шапке и подвале сервиса `data-version-service="<id>"` - версия подставится из конфигурации.
5. Создайте свой экземпляр `IDBStore` с уникальным `dbName` и уникальным ключом; для загрузки/сохранения используйте `createReportStorage`.
6. Добавьте `./Services/<имя>/index.html` в массив `SHELL` в `sw.js`, иначе `test/config.test.js` упадёт, а сервис не попадёт в precache.
7. Добавьте пример XLSX в `not indexed/samples_XLSX/` (локально, без коммита), тесты и запись в `NEWS_CHANGES`.
8. Уберите из `<style>` нового сервиса дубли уже описанного в `shared/css/common.css` (сброс, кнопки, модалки, пагинация, загрузка и т.д.), оставив только `:root`-переменные и уникальные компоненты.
9. Обновите версию портала и версию нового сервиса, затем прогоните `node --test`.

## Правила разработки

- **Никаких сборщиков и фреймворков.** Сервис - самостоятельная HTML-страница; общий код только в `shared/`.
- **Русский язык.** Комментарии, интерфейс, сообщения об ошибках и документация - на русском.
- **Версии не хардкодятся в HTML.** Только `shared/js/config.js` и `data-version-service`.
- **`package.json` синхронизирован с `PORTAL_CONFIG.version`.** Это проверяет тест.
- **IndexedDB изолирована по сервисам.** Не переиспользуйте `dbName` между сервисами.
- **Не меняйте примеры XLSX без обновления тестов.** Ожидаемые числа в тестах привязаны к конкретным файлам.
- **Учитывайте ограничения `parseXLSXFile`:** читается только первый лист, `cellDates: true`, заголовки - по индексу (по умолчанию первая строка). Перед `sheet_to_json` диапазон листа расширяется по фактическим ячейкам, если файл сохранён с занижённым `!ref`. Для нестандартных книг (например, аномалии) используется собственный разбор.
- **Проверяйте `SHELL` и `config.js` при добавлении папки с `index.html`.** `test/config.test.js` требует полного соответствия.
- **Проверяйте пути с кириллицей и пробелами.** В URL их нужно экранировать; для новых папок лучше латиница.

## Известные проблемы и нюансы

1. **Корень проекта - git-репозиторий.** Вложенный репозиторий `LogisticAnalytics/.git` убран; `LogisticAnalytics/README.md` теперь обычная папка документации в корневом репозитории. Для деплоя используется GitHub Actions, а не публикация корня ветки.
2. **В «Аномалиях склада»** в тексте инструкции осталась устаревшая фраза про кнопку «Загрузить пример», хотя самой кнопки нет.
3. **`file://`** ограничивает Service Worker и иногда IndexedDB. Для проверки PWA и офлайна используйте `localhost` или HTTPS.
4. **Данные в IndexedDB привязаны к origin.** После смены адреса (например, с `file://` на `localhost`) сохранённые отчёты не переносятся автоматически.
5. **Термин единый - SKU.** Все метки интерфейса и тестов используют SKU.
